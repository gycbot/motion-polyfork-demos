# Skill-first task

Goal: before doing a new task, lock a Skill path and smoke it; deliver applied output, not research prose. For production work, quality is fixed **before** spending quota, not caught by after-the-fact review.

1. **Name the task in one line** (outcome + medium). Mark if it is new (new platform, format, UI, role split, copy system, tool stack).
2. **Search Skills in order**: (a) user-named / bookmark-to-apply items this turn, (b) `standing/SKILL_ROUTER.md` and local workflows on disk, (c) Cursor-managed / installed plugin skills, (d) public GitHub/X only if a–c miss.
3. **Pick one primary Skill** (optional 0–2 references). Refuse five parallel empty reads.
4. **Read** that Skill's SKILL.md and only the references needed for the first smoke step.
5. **Production start gate** (content / visual / H5 / copy / video only; skip for pure ops, debugging, rule edits and say so). Write once into the existing brief/contract, missing any item = do not start:
   - ① ≥3 refined, high-like/high-save references from ≥2 platforms (link, visible likes/saves, capture time; if not visible say so, never invent numbers).
   - ② Primary skill absolute path + its verified sample/receipt + the exact step/component you will reuse and where it lands. A skill name alone is not reuse.
   - ③ An observable quality bar written against those references (audience, platform, locked style).
   - Same-series small edits (swap code, fix text, local fix) inherit still-valid references and bar; write only the diff. Do not re-search three samples per tweak.
   - References teach structure and execution; they never override owner mother-copy, product facts, character or account locks.
6. **Minimum proof per medium before scaling** (done by the producer itself, not a new user review): still = one sample frame; motion = one short local motion clip; voice = one short line; H5 = mobile first screen + real click; copy = audience/source/mother-copy diff. Static frames, fps numbers, file existence or a passing check do not prove motion, sound or interaction.
7. **Execute** the real task using that Skill only after the proof matches the bar. Blockers: re-read the Skill first; do not invent a parallel process. Redo only the affected module, not the whole piece.
8. **Deliver once**: one finished result that meets the bar and actually opens/plays, with a reuse line in the HANDOFF: `refs / inherited | skill + verified scope | step/component used | proof path | diff this time`. Never send a weak draft for the owner to find problems; never name a placeholder or half-product final. If truly blocked, report the gap.

Hard rules: no paid stacks unless the owner said so; compliance/publish gates and §26 topic approval still win over Skill steps; this gate adds no review role and no routine; do not treat long scout writeups as delivery. How to generalize a correction lives in `user-taste-transfer`, not here.
